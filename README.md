# SkinCare Copilot

基于 **Java 17、Spring Boot、LangChain4j 和 RAG** 的可扩展个人护肤管理 Agent 演示项目。目标是将用户已确认的皮肤画像、会话上下文、可追溯的护肤知识与工具调用结合起来，为不同任务提供有依据、可解释、保守的个性化建议。

> **项目定位：多能力护肤助手，不是单一的护肤品评分器。** 护肤品适用性评估是其中一个持续迭代的核心模块；后续还计划加入日常护理规划、饮食与过敏原校验、长期记忆和提醒等能力。目前只完成了部分功能，计划中的能力不代表已经上线。项目不提供诊断、处方、药物剂量或确定的治疗效果；开发、测试仅使用虚构用户与演示输入。

## 核心模块：护肤品适用性评估（持续开发）

这个模块要回答的不只是“含不含某个成分”，而是 **“特定用户在特定部位、特定皮肤状态下，是否有足够依据考虑使用这款产品？”** 例如同一款润肤霜，面部 T 区与身体使用的关注因素可能不同；不能仅凭一个“油皮/脂皮”标签给出一刀切结论。

### 目标执行链路

```text
用户输入具体产品名称／包装 INCI（可选第二款产品）
   ↓
解析产品实体与具体版本（品牌、完整名称、地区、配方版本）
   ↓
优先查询该用户已确认保存的包装 INCI
   ├─ 有：明确标记为用户提供，检查格式与版本
   └─ 无：查官网候选页；只有页面明确标注全成分且产品名、市场、版本可核对时提取
   ↓
成分标准化（中英文 INCI、别名、来源与置信情况）
   ↓
Java 确定性检查（已确认的过敏成分命中、来源完整性等）
   ↓
检索成分证据和场景规则（法规/刺激/致敏/功效/特定皮肤问题）
   ↓
结合已确认画像 + 本次使用部位 + 当前状态 + 使用诉求
   ↓
输出：结论与证据等级／关键成分／分部位建议／未知项／何时停用或就医
```

**当前真实链路比目标链路短。** `POST /api/products/search` 定位官网候选页；新增严格的官网页面全成分提取，但仅支持明确标注全成分且能核对产品名、市场、版本的页面，详见[官网全成分提取说明](docs/official-product-ingredients.md)。`POST /api/ingredients/analyze` 可以解析取得或粘贴的 INCI，并对本次明确确认的过敏成分执行 Java 强制匹配。当前 `assessment.decision` 仅有 `AVOID_CONFIRMED_MATCH` 与 `UNKNOWN`，没有一般人群的“安全认证”或医学适用性评级。没有可靠完整成分表时，应返回信息不足，不从产品名字或搜索摘要猜测配方。

### 用户输入与结果设计

**输入**：产品完整名称及版本、包装或可信来源的完整 INCI、用户已确认肤质／皮肤问题、使用部位（面部 T 区、面颊、身体等）、当前状态（稳定/不适/未知）、目标（保湿、清洁、控油等）、自述敏感、已确认过敏的具体成分。敏感描述与诊断、一般过敏原与具体成分过敏应区分；临时填入的信息不得静默改写持久画像。

**输出**：优先说明“已确认成分匹配需避免 / 暂无足够信息判断 / 在证据充分时给出带条件的使用建议”，逐项列出实际命中的依据、适用范围与不确定性。对面部与身体、不同状态应分别评估，而非输出泛化的产品好坏分数。未知浓度、配方工艺、个体耐受性时不得声称能预测实际刺激、致痘或治疗效果。

### 计划建设的四层知识与规则体系

| 层次 | 数据内容 | 设计目的 |
| --- | --- | --- |
| 1. 法规与安全证据 | 地区、用途、浓度条件下的禁限用规定；权威原始评估结论 | 做有条件的法规核验，不把“限用”等同于“所有用户禁用” |
| 2. 成分风险与功效标签 | 按具体 INCI 记录致敏、刺激、功效及可能与痤疮/脂溢性皮炎等相关的证据 | 为检索和规则匹配提供材料，避免简单黑名单 |
| 3. 机制与场景规则 | 证据来源、研究对象、机制假设、使用部位、皮肤状态和建议 | 将“研究线索”与“可用于个人判断的强证据”区别开 |
| 4. 产品级配方库 | 具体产品的完整 INCI、品牌/地区/版本、原始链接和核验时间 | 确保先拿到真实配方，再做逐项分析 |

实施建议：先建立少量**人工核验的示例产品 + 20–50 个高频成分**，为每个标签记录来源、证据强度、适用人群和更新时间；再逐步扩大覆盖。以脂溢性皮炎/马拉色菌相关文献作为一个专项研究场景，但**不能**把“C11–C24 脂质”“脂肪醇”“厚重霜体”等直接写成普适禁用规则，体外研究不能自动推导个人是否适用。单成分兔耳试验的 0–5 致粉刺评分，也不能直接决定成品风险。

候选来源包括 NMPA、SCCS、CIR、公开研究和第三方成分数据库/API。**候选 ≠ 已接入或已验证**。特别是 [Open Cosmetics](https://github.com/AndyZhuang/opencosmetics)：经此前源码检查，其原料检索、配方规则工具不能替代“任意中文商品对应的官方完整 INCI”；内置规则也不是个人脂溢性皮炎风险判定。数据许可、版本、调用成本和产品级覆盖必须单独验证。详情见 [产品工作流与资料核查](docs/product-workflow-review.md)、[成分资料记录](docs/ingredient-sources.md) 与 [马拉色菌文献发现](docs/malassezia-literature.md)。

### 技术实现原则

- **Java 管硬约束，LLM 管可解释的文本生成**：已确认过敏成分的名称匹配由后端控制，不能让模型绕过；模型只能使用已检索来源解释，不能编造 INCI、浓度和临床结论。
- **工具与 RAG 分工**：产品级 `product_lookup` 解决“成分是什么”；成分字典和规则引擎解决“已知证据是什么”；RAG 查找相关原文与适用边界；Agent 负责协调缺失信息、工具调用和输出。无需为了“Agent”标签强行引入多 Agent。
- **失败可控**：查询无结果、产品版本不明、INCI 不完整、规则无证据、模型调用失败时明确降级；记录检索来源、规则命中与耗时，不保存无必要的敏感信息。
- **可验证**：以虚构画像和可核验配方构造测试集，测产品解析准确率、已确认过敏成分召回、来源引用正确率、证据不足时的拒绝臆断、分部位场景一致性和端到端成功率。

## 运行 Day 1～3

要求 JDK 17+ 和 Maven 3.9+。项目以 Java 17 为编译目标，固定 Spring Boot 3.5.16、LangChain4j 1.22.0。默认使用 DeepSeek 的 OpenAI 兼容接口，模型需支持工具调用才能查询画像。

```bash
export SKINCARE_LLM_API_KEY='在终端或环境设置里填入密钥'
# 默认：SKINCARE_LLM_BASE_URL=https://api.deepseek.com
# 默认：SKINCARE_LLM_MODEL=deepseek-flash
mvn test
mvn spring-boot:run
```

在 VS Code 中打开项目文件夹，使用集成终端设置 `SKINCARE_LLM_API_KEY` 并运行上面的 Maven 命令。Windows PowerShell 的设置方式是 `$env:SKINCARE_LLM_API_KEY="你的密钥"`。如果改用 `deepseek-v4-pro`，再设置 `SKINCARE_LLM_MODEL=deepseek-v4-pro`。这里使用的是 OpenAI 兼容接口地址；`https://api.deepseek.com/anthropic` 是另一种协议的地址，不适用于当前 `OpenAiChatModel`。请以 DeepSeek 控制台显示的可用模型和工具调用支持情况为准。

打开本机 `http://localhost:8080/`。先为虚构用户填写并勾选确认画像，再点击“保存画像”或“查询画像”。画像写入项目目录下的 `data/`（已被 Git 忽略）；再次启动应用仍可读取。未勾选确认时，后端拒绝保存。`GET /api/profiles/{userId}` 查询，`PUT /api/profiles/{userId}` 保存，保存 JSON 例如 `{"skinType":"油性","allergens":["花生"],"confirmed":true}`。

页面聊天发送 `POST /api/chat`，JSON 为 `{"userId":"demo-user","sessionId":"session-1","message":"我的肤质是什么？"}`，返回 `{"answer":"..."}`。同一用户和会话 ID 会承接近期对话；点击“开始新会话”会换一个会话 ID。模型可主动调用只读画像工具，服务日志会出现 `tool=getConfirmedProfile`。没有密钥时聊天接口返回 503；空消息或缺少会话 ID 返回 400。不要把密钥写进仓库或网页。

近期对话由 LangChain4j `MessageWindowChatMemory` 保留最近 20 条消息，只存在于当前后端进程，重启后消失；已确认画像保存在 H2 文件中，重启后仍可查询。记忆键同时包含用户 ID 和会话 ID，避免不同用户或会话共用上下文。页面在当前标签页的 `sessionStorage` 保留会话 ID；刷新页面会沿用会话，点击“开始新会话”会换 ID。当前没有过期清理或跨进程共享记忆。用户 ID 只是演示标识，尚无登录认证，请勿放入真实个人资料。事实性护肤及饮食问题会检索当前小型知识库；命中片段不等于所有回答内容都已被人工核实，请核对显示的原文与适用范围。

当前版本把常见餐食请求送到 `MealPlanService`：需要先保存已确认画像，模型输出三餐 JSON 草稿，Java 检查每餐食材与已确认过敏原及已建模别名；违规最多重试两次，仍失败则不展示任何草稿。此校验只覆盖演示样例，不能保证现实过敏风险。

## Day 4：独立知识片段检索

`mvn verify` 会运行原有画像/会话/聊天测试和新增导入、切分、本地中文向量检索及接口测试。不需要模型 API 密钥。新依赖为 `langchain4j-embeddings-bge-small-zh-v15-q:1.22.0-beta32`（与 LangChain4j 1.22.0 配套），模型和分词器随 Maven 依赖提供；Embedding 在本机 CPU 执行，不调用 DeepSeek，也不在启动时抓取官网。首次安装需下载 ONNX Runtime 等依赖。

启动命令仍是 `mvn spring-boot:run`。页面新增“知识片段与来源”，与现有聊天分别使用独立接口：

```bash
curl http://localhost:8080/api/knowledge/sources
curl -X POST http://localhost:8080/api/knowledge/search \
  -H 'Content-Type: application/json' \
  -d '{"query":"痤疮皮肤如何清洁？","topK":3}'
```

检索输入最多 500 字符，`topK` 默认 3、允许 1～5。返回片段、来源标题/章节/链接、查阅日期、原文摘录或标题和相似度，不返回生成式回答。分数为 LangChain4j 的归一化余弦相似度 `(cosine + 1) / 2`，最低 0.75，只用于检索排序，不是医学可信度或证据等级；阈值尚未用正式知识条目校准。

启动时导入 `src/main/resources/knowledge/entries.json`，字段校验后按来源分别切分：最多 180 个 Unicode 码点、重叠 30 个码点、优先句末；保留确定性片段 ID 及原译文中的 UTF-16 起止位置。使用 BGE 中文量化模型生成 512 维向量，内存索引每次启动重建，正式条目随仓库保存。少量条目采用串行计算，无需向量数据库。测试夹具只在测试中使用，不会进入正式索引。

`entries.json` 现含 6 条经 AAD/NICE 官网核对的短条目、14 条温唯文章观点摘要和 2 条注明体外实验条件的 Europe PMC 论文摘要，覆盖痤疮饮食研究的不确定性、玫瑰痤疮的个人诱因与护肤、12 岁以下特应性湿疹的诱因评估与保湿。原文与适用范围见 [Day 4 来源记录](docs/day4-sources.md)。网页展示命中的片段与原文出处，并区分机构资料和作者观点；“泛红”不能据此自动诊断为过敏或玫瑰痤疮。

## Day 5～6：带来源的聊天与问题路由

`POST /api/chat` 仍接收 `userId`、`sessionId`、`message`。响应增加 `route` 和 `sources`；原有 `answer` 保留。四种路由是 `SMALL_TALK`、`KNOWLEDGE`、`PROFILE`、`COMBINED`。日志记录路由结果。规则在 `ChatRouter` 中明确列出：涉及皮肤、饮食、成分等事实的问题进入检索；直接问已确认画像走画像分支；同时涉及个人情况和事实的请求走综合分支。规则是第一版可读、可测的保守匹配，不宣称能覆盖所有表述。

知识/综合分支从当前小型资料库检索最多 3 个片段。空结果直接说明资料不足，不调用模型；有结果时仅把命中片段提供给模型，Java 根据实际命中附上来源，网页展示出处。综合分支还读取 H2 中已确认的画像；模型仍可调用只读画像 `@Tool`。聊天中的推断不会写入画像。模型生成内容可能有遗漏或偏差，请查看附带的原文及适用范围；检索相似度阈值 0.75 是演示设置，尚未用系统评测校准。

餐食方案由独立结构化生成与 Java 校验流程处理；资料只支持说明痤疮与饮食研究的不确定性，不支持声称餐食能治疗痤疮。真实模型回答需设置 `SKINCARE_LLM_API_KEY`，默认 DeepSeek 兼容地址与 `deepseek-flash`；无密钥可运行测试、独立检索以及知识依据不足分支。`mvn verify` 的测试用本机假模型覆盖检索片段进入提示词、来源只来自命中数据、缺少依据时不调用模型，以及容易误分的短事实问题。

## 具体护肤品成分来源查询（试验性）

Day 6 后新增只读产品页面查询能力。在聊天框上方填写**包装上的完整产品名**但不填写成分表时，页面会寻找可信品牌官网的具体产品页面。`POST /api/products/search` 接收 `{"productName":"完整产品名"}`。目前接入 Tavily Search API，需在本地 PowerShell 的运行窗口设置 `SKINCARE_SEARCH_API_KEY`，另用逗号分隔的 `SKINCARE_PRODUCT_OFFICIAL_HOSTS` 指定你已核实属于该品牌官网的域名。只有 HTTPS、精确匹配所配域名且页面标题包含产品全名的搜索结果会展示；官网域名或搜索密钥缺失时返回明确提示。不要把密钥写入仓库。此接口不会发送用户 ID、画像或聊天内容到搜索服务，只发送产品名。

**搜索摘要不是完整成分表。** 搜索接口只定位官网候选页；独立的官网提取器在身份信息和全成分标签都可核对时才返回候选列表，不能判断个人对哪个成分过敏。即使日后核实完整配方，也只能把成分与已确认的资料对照、指出待专业评估的线索；单凭一次皮肤反应及配方列表无法确认致敏成分。品牌名如“薇诺娜”无法确定是哪一款产品；需要完整产品名，最好有官方产品页。聊天里说“我可能对某产品过敏”时，若只给品牌名，会要求完整产品名；若给出具体产品名，会自动调用同一只读查询。缺少市场和版本时只返回官网候选链接与不足说明，不推断个人致敏成分。搜索仍需配置密钥和可信官网域名。

## 同一聊天窗口中的护肤品成分解读与双产品对比

聊天输入框上方的可展开区域可填写具体产品全名，或粘贴一款或两款完整成分表；填写肤质、关注问题、使用部位、当前状态、自述敏感和已确认过敏的**成分**后，在同一个聊天窗口提问和查看回答。只有产品名时会查询官网候选页；若另外提供市场和版本，系统才尝试读取满足严格条件的官网全成分区域。搜索摘要不会当作完整 INCI。`POST /api/ingredients/analyze` 使用相同字段；只有 `first` 必填，`second` 可省略。需要 `SKINCARE_LLM_API_KEY` 生成自然语言分析；缺少密钥或模型调用失败时只返回成分解析、强制命中与明确的能力不足说明。此模块没有修改原有画像或餐食逻辑。

调用顺序：`IngredientController.analyze` → `IngredientService.analyze` → `IngredientNames.parse` 保留原文与顺序并用小型别名表标准化 → 读取已有画像中的肤质（本次肤质优先）→ Java 对本次明确确认的过敏**成分**进行逐项精确/已知别名匹配 → 复用 `KnowledgeService.search` 检索相关 AAD 片段 → 若命中已确认过敏成分，Java 直接返回警示而不调用模型；否则由模型输出 JSON `answer`，Java 校验结构并返回实际引用的来源。画像现有 `allergens` 是一般过敏原，**不会**被自动解释为已确认过敏成分；本次确认的成分也不会持久写入画像。未勾选确认时拒绝把填写的成分当作过敏史。

当前名称表覆盖香精、烟酰胺、甘油、棕榈酸、鲸蜡硬脂醇、部分神经酰胺等少量示例及已知别名；其余名称只做字面标准化。相同名称的匹配也不能证明个人对实际产品的反应。已有知识库中仅 [AAD 玫瑰痤疮无香料建议](https://www.aad.org/public/diseases/rosacea/triggers/tips) 与 [AAD 接触性皮炎概述](https://www.aad.org/public/diseases/eczema/types/contact-dermatitis) 可用于相关解释，均已在 `entries.json` 记录标题、原文、链接和 2026-10-24 核实日期。前一条适用范围为玫瑰痤疮护理；后一条区分刺激和过敏。没有针对烟酰胺浓度、甘油实际效果或具体产品功效的已核实资料，回答应明确资料不足。温唯成分目录的 14 篇文章已整理为可检索的作者观点摘要；检索命中时必须标明作者观点，不把文章概括为临床证据。

这是独立于九天主线的新增功能；Day 7～9 的餐食与项目收尾功能已另行实现。成分分割依赖用户提供的逗号/顿号/分号/换行分隔文本，不识别图片、括号内复杂复合名称或未知同义词；无法由列表推算准确浓度、配方工艺及实际功效。模型的自然语言结论仍可能有错误，强制匹配和来源链接由 Java 控制。

### 温唯文章目录（科普阅读层）

`knowledge/creator-articles.json` 收录用户给的成分目录中 14 篇文章的作者、标题、原文链接、发布日期、查阅日期与主题。`knowledge/entries.json` 增加每篇文章的简短观点摘要并进入现有向量检索；不复制全文或成分风险表。回答需要把温唯文章标为作者观点，AAD/NICE 标为专业资料，不把博客观点提升为个人诊断或确定功效。`GET /api/ingredients/articles` 可查看文章目录。来源核对及取舍见 `docs/ingredient-sources.md`。

需求草稿中的候选资料与未核实主张逐项记录在 [产品工作流与资料核查](docs/product-workflow-review.md)。

常见的“我可以用某某面霜吗”等具体产品问句也会先走 `ProductQuestionDetector` 和 `ProductSearchService`，查询官网候选页；用户提供市场和版本时才尝试严格提取页面明确标注的全成分。提取失败仍说明资料不足，不会把搜索摘要写成配方或个人适用结论。该识别只覆盖小型规则集，不能保证识别所有商品名称；尚无任意商品的通用配方库。

## 马拉色菌文献发现工具

`bash scripts/discover-literature.sh /tmp/skincare-literature-candidates.json` 批量检索 Europe PMC，并保存去重的文献元数据供人工审读。它不抓取全文、不生成个人风险评分，候选文献也不会自动进入 RAG。证据核查流程和当前访问状态见 [文献发现记录](docs/malassezia-literature.md)。

用户勾选“这是该具体版本包装上的完整成分表”后，成分表会按用户 ID 保存到 H2 的 `user_product_ingredients`；以后在同一聊天窗口问同名产品，后端先读该用户保存的文本，再考虑联网搜索。记录只代表虚构用户自述，不是官方配方。成分分析响应的 `assessment.decision` 只有 `AVOID_CONFIRMED_MATCH`（本次已确认过敏成分名称命中）和 `UNKNOWN`（个人适用性未知）；`signals` 带来源和实验局限，不是致痘分数。云环境如设置 `HTTPS_PROXY`，应用启动时会配置 Java HTTP 客户端使用代理并使 localhost 直连；本机无该变量时维持默认网络行为。

“查看本用户已保存的成分表”可将记录载入第一款或第二款，再在原聊天窗口分析两款；也可删除本用户保存的记录。后端对应 `GET /api/products/saved/{userId}` 和 `DELETE /api/products/saved/{userId}?productName=...`。这些是虚构用户演示数据，当前项目仅以用户 ID 隔离记录，尚无登录认证，不能用于真实个人资料。
